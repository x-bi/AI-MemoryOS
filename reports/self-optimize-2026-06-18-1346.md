## 详细借鉴点

### 1. 记忆查询的合成与显式 gap analysis 输出
- 来源: [garrytan/gbrain](https://github.com/garrytan/gbrain) (channel: github)
- 相关性: GBrain 在返回答案时不仅给出引用，还显式列出'尚未掌握的部分'。AI-MemoryOS 当前 L2 读取偏检索式，可在 skills/memory-curator 或 _index 查询路径中加入 gap report，让模型主动暴露记忆空缺，便于触发 proposal。
- 接入设想: skills/memory-curator/SKILL_SPEC.md、skills/memory-auditor/、workflows/、_index.md 中的检索流程
- 工作量 / 价值: M / med
- 风险: 若 gap 描述未与 proposals/pending 联动，可能流于格式化输出
- 验证: fits=true, 符合 MemoryOS 让模型暴露记忆空缺并触发 pending proposal 的现有路径

### 2. 条目间自动建立类型化边（typed edges）的轻量图层
- 来源: [garrytan/gbrain](https://github.com/garrytan/gbrain) (channel: github)
- 相关性: GBrain 在写入页面时无 LLM 调用就抽取实体引用并建立 attended / works_at 类型边，检索准确率显著高于纯向量。MemoryOS 当前只靠目录与 router 路由，可在 markdown frontmatter 或维护脚本里加入轻量类型链接（如 relates_to / supersedes / depends_on）形成图。
- 接入设想: templates/、core/memory-rules.md、tools/ 维护脚本、router/domain-map.md
- 工作量 / 价值: M / med
- 风险: 类型边过度设计会与现有 Markdown + Git 极简事实源原则冲突
- 验证: fits=unclear, 类型边可能与 Markdown+Git 极简事实源原则冲突，需先小范围验证

### 3. 夜间/离线一致性巩固守护进程（consolidation daemon）
- 来源: [garrytan/gbrain](https://github.com/garrytan/gbrain) (channel: github)
- 相关性: GBrain 用 cron 跑 66 个后台任务做引用修复与记忆巩固。MemoryOS 当前 proposal 晋升靠人工，可借鉴定时维护脚本：自动扫描悬挂链接、过期 future-directions、未审核 pending、stale memory，但只生成报告不自动写入。
- 接入设想: tools/、workflows/、proposals/future-directions/、logs/
- 工作量 / 价值: M / med
- 风险: 需严格遵循只读 + pending 写入边界，避免后台任务越权改正式规则
- 验证: fits=true, 只读扫描 + pending 报告完全契合现有 proposal 边界与维护脚本定位

### 4. llms.txt / llms-full.txt 双层入口供模型一次抓取
- 来源: [garrytan/gbrain](https://github.com/garrytan/gbrain) (channel: github)
- 相关性: GBrain 同时提供 AGENTS.md、CLAUDE.md 与 llms.txt（仅地图）/llms-full.txt（地图+核心文档内联），方便不同读取预算的模型。MemoryOS 已有 adapter 分层，可补一份 llms.txt 地图，作为 L1 borderline 任务的轻量入口。
- 接入设想: 仓库根目录新增 llms.txt、与 _index.md / adapters/*/bootstrap.md 互链
- 工作量 / 价值: S / low
- 风险: 信息冗余，需要与 _index.md 同步维护
- 验证: fits=unclear, 已有 adapter 分层与 _index.md，新增入口收益低且维护负担重

### 5. skill 之间的自动冲突检测机制
- 来源: [yusufkaraaslan/Skill_Seekers](https://github.com/yusufkaraaslan/Skill_Seekers) (channel: github)
- 相关性: 本仓库 skills/registry.json 与 skills/<skill>/SKILL_SPEC.md 持续增长，缺乏触发边界/命名/职责重叠的检测；Skill Seekers 将其作为 skill 打包流程的标配能力。
- 接入设想: tools/ 下增加 skill-conflict-check.ps1，或在 router/skill-map.md / skills/registry.json 校验阶段引入触发边界重叠扫描；可结合 memory-auditor / skill-updater skill。
- 工作量 / 价值: M / med
- 风险: 冲突判定阈值不当会产生误报，需要先用现有 skill 做样本回归。
- 验证: fits=true, registry.json 与 SKILL_SPEC 持续增长，触发边界冲突检测对当前 skill 体系直接有用

### 6. 把外部文档/仓库/PDF 结构化为 skill 草稿的预处理流水线
- 来源: [yusufkaraaslan/Skill_Seekers](https://github.com/yusufkaraaslan/Skill_Seekers) (channel: github)
- 相关性: 本仓库 skill/proposal 目前依赖人工沉淀；该项目演示了一条「source -> 结构化知识资产 -> 多目标导出」的稳定流程，可启发把外部资料先落到 proposals/pending/ 的标准化草稿。
- 接入设想: workflows/ 下新增「外部资料转 pending proposal」工作流，配合 templates/ 的 skill/proposal 模板，落点仍在 proposals/pending/。
- 工作量 / 价值: L / low
- 风险: 若不严格走 pending 审核，会绕过 L3 写入边界，引入未审计内容。
- 验证: fits=false, 本仓库强调人工审核与精简事实源，重型预处理流水线偏离 personal memory 定位

### 7. context 用量环形指示器作为读取预算可视化
- 来源: [nesquena/hermes-webui](https://github.com/nesquena/hermes-webui) (channel: github)
- 相关性: Memory OS 强调 L2 不超过 2k / 维护 5k-8k tokens 的预算约束，但目前没有可视化反馈；Hermes WebUI 的 circular context ring 是一个轻量 UX 信号样式，可借鉴到 dashboard/home.md 或 Final Trace 输出。
- 接入设想: dashboard/home.md 增加预算占用展示；或在 Final Trace 末尾扩展 budget 字段（但需评估是否打破共享 gate 格式）。
- 工作量 / 价值: S / low
- 风险: 扩展 Final Trace 字段会影响 Codex/Claude 共享 gate，必须经 cross-adapter sync 流程。
- 验证: fits=false, 扩展 Final Trace 字段会破坏 Codex/Claude 共享 gate，且为纯 UX 装饰收益低
