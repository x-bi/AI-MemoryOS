## 详细借鉴点

### 1. Prompt-as-Engineering 分层：模板 vs 可工程化 prompt
- 来源: [ai-boost/awesome-prompts](https://github.com/ai-boost/awesome-prompts) (channel: github)
- 相关性: awesome-prompts 把 prompt 世界分为「模板派」和「工程派」，后者强调测试、回归、自动优化。Memory OS 的 prompts/ 目前只有模板，缺少可评估、可回归的 prompt 工程化思路。
- 接入设想: prompts/ 目录可引入 prompt 工程化分层；skills/registry.json 可为 skill 内 prompt 增加 eval 字段
- 工作量 / 价值: M / med
- 风险: 工程化 prompt 需要配套 eval 框架，当前 evals/ 较薄，可能落地困难
- 验证: fits=False, prompts/ 是轻量路由提示（每文件 100-160 字节），不是工程化 prompt 系统；对个人 markdown 系统引入 eval 框架属过度工程化

### 2. Context Engineering 章节对 L0-L3 Gate 的补强
- 来源: [ai-boost/awesome-prompts](https://github.com/ai-boost/awesome-prompts) (channel: github)
- 相关性: awesome-prompts 的 Context Engineering 章节汇总了 token 预算、上下文窗口管理、记忆持久化的工程实践，可直接补强 Memory OS 的 L0-L3 Gate 读取预算策略。
- 接入设想: core/memory-rules.md 读取预算部分；router/intent-map.md 路由策略
- 工作量 / 价值: S / med
- 风险: Context Engineering 领域演进快，引用的具体技术可能短期过时
- 验证: fits=False, memory-rules.md 已有完善的读取预算策略（2k 默认/5k-8k 维护），context engineering 主要解决 LLM 应用层问题，对 git+markdown 系统意义有限

### 3. Agent Harness Designer prompt 模式映射到 adapter 设计
- 来源: [ai-boost/awesome-prompts](https://github.com/ai-boost/awesome-prompts) (channel: github)
- 相关性: awesome-prompts 收录了 Agent Harness Designer prompt，涵盖 tool minimization / approval gates / memory compaction / rollback 等原则，与 Memory OS 的 adapter gate + skill + proposal 流程高度同构，可提炼为 adapter 设计 checklist。
- 接入设想: adapters/ 下各适配器的 gate.md 和 external-config.md；skills/ 各 skill 的 SKILL_SPEC.md
- 工作量 / 价值: S / high
- 风险: 不同模型 adapter 能力差异大，checklist 需按 adapter 分化而非一刀切
- 验证: fits=unclear, 概念同构但'adapter 设计 checklist'定义模糊；当前仅 2 个活跃适配器（Claude/Codex），需求不迫切，需先明确 checklist 具体产出

### 4. 跨模型交叉审阅工作流
- 来源: [wanshuiyin/Auto-claude-code-research-in-sleep](https://github.com/wanshuiyin/Auto-claude-code-research-in-sleep) (channel: github)
- 相关性: ARIS 的 cross-model jury 让不同模型互审输出，可增强 Memory OS 多适配器场景下 proposal 审核的可信度，目前 Memory OS 的审核仅依赖人工单点审核。
- 接入设想: workflows/ 新增 cross-model-review 流程；router/ 增加多模型审阅路由策略

- 验证: fits=False, 个人记忆系统引入多模型 jury 审阅增加 token 成本和延迟，收益远低于生产系统场景；人工单点审核对当前规模足够

### 5. Skill 跨适配器可移植性声明

### 9. 事实时间窗口与自动失效机制
- 来源: [Graphiti](https://github.com/getzep/graphiti) (channel: web)
- 相关性: Graphiti 为每条事实附加 valid_at/invalid_at 时间戳，旧事实被失效而非删除，支持任意时间点查询。Memory OS 当前记忆无时效性标注，工程经验可能随项目演进过时。
- 接入设想: 记忆页 markdown frontmatter 增加 valid_from/valid_until 字段；tools/ 验证脚本检查过时记忆
- 工作量 / 价值: M / high
- 风险: 需人工或规则判定失效时间，自动化可能误标活跃经验为过时
- 验证: fits=True, 记忆无时效性标注（验证无 valid_from/valid_until 字段），工程经验随项目演进过时是实际问题，可从 frontmatter 字段+验证脚本低成本起步

### 10. 多信号检索：语义+关键词+实体融合

- 相关性: Mem0 将语义搜索、BM25 关键词、实体匹配并行后融合评分，检索精度显著优于单一向量搜索。Memory OS 当前检索依赖文本 grep，跨页关联弱。
- 接入设想: adapters/mcp/ 增加混合检索 tool；tools/ 增加构建索引脚本（embedding + 实体抽取）
- 工作量 / 价值: L / high
- 风险: 引入向量数据库依赖，增加部署复杂度；小规模仓库 grep 已足够
- 验证: fits=False, 个人 markdown 仓库规模小，MCP memory_search 已提供文本检索；引入向量数据库和 embedding 管道是过度工程化，候选自身风险也承认'grep 已足够'

### 11. ADD-only 提取策略：追加不覆盖
- 来源: [Mem0](https://github.com/mem0ai/mem0) (channel: web)
- 相关性: Mem0 新算法用单次 LLM 调用只做 ADD 不做 UPDATE/DELETE，记忆只增不改。与 Memory OS 的 pending proposal 写入隔离理念高度一致，可强化写入安全边界。
- 接入设想: skills/memory-curator/ SKILL_SPEC.md 增加追加优先原则；tools/validate-memory-os.ps1 检测直接修改已接受规则的违规
- 工作量 / 价值: S / med
- 风险: 纯追加可能导致记忆膨胀，需配合定期整理/归档流程
- 验证: fits=False, Memory OS 已通过 L3 gate + proposals/pending 隔离实现写入安全边界，追加优先原则已隐含在提案流程中，validate-memory-os.ps1 可增量加强但非必需

### 12. 三阶段记忆操作门控：写入→图谱构建→检索

- 接入设想: adapters/claude/external-config.md 或 adapters/codex/external-config.md 的写入流程增加异步索引步骤
- 工作量 / 价值: M / med
- 风险: 增加写入延迟；需确保异步索引不阻塞主流程

### 13. 实体-关系-观察三元组结构化链接
- 来源: [MCP Memory Server](https://github.com/modelcontextprotocol/servers/tree/main/src/memory) (channel: web)
- 相关性: MCP Memory Server 用 Entity-Relation-Observation 三层模型，实体间有有向关系边。Memory OS 当前记忆页间主要靠 [[wiki-link]] 人工关联，缺乏结构化关系类型。
- 接入设想: 记忆页 frontmatter 增加 relations 字段（如 relates_to:: [[page]] type:: depends_on）；tools/ 可视化关系图
- 工作量 / 价值: M / med
- 风险: 增加维护成本；人工标注关系类型可能不及时或不一致
- 验证: fits=unclear, 缺乏结构化关系类型属实，但人工标注有向关系边维护成本高；个人系统规模下 wiki-link 仍是务实选择，需评估自动推断关系的可行性

### 14. 记忆块角色分离：human/persona/project 独立存储

- 风险: 分类标准需维护；类型过多可能增加路由复杂度
- 验证: fits=unclear, proposal 模板已有 scope 字段（Global/domain/stack/project-specific）部分覆盖分类需求；memory_type 增加路由精度有理论价值，但分类标准维护成本需权衡

### 15. 溯源 Episode 机制：每条记忆回溯原始输入

### 16. Reference Skills vs Pipeline Skills 分类法
- 来源: [Mem0](https://github.com/mem0ai/mem0) (channel: web)
- 相关性: Mem0 将 skills 分为 reference skills（始终活跃的上下文）和 pipeline skills（按需触发的工作流），与 Memory OS 的 L0-L3 Gate + skills/ 体系互补，可细化 skill 触发策略。
- 接入设想: skills/registry.json 为每个 skill 增加 trigger_mode 字段（always_on / on_demand）；Gate 逻辑中 always_on skill 在 L1+ 自动加载上下文
- 工作量 / 价值: S / med
- 风险: always_on skill 过多会增加每次对话的上下文开销
- 验证: fits=False, L0-L3 gate + description 匹配已隐式实现触发模式区分（L0 不触发、L1+ 按需触发），显式 trigger_mode 增加配置复杂度但实际路由收益有限

### 17. 用户自定义 slash command 模板模式

### 18. 跨会话记忆自动提取与存储工具
- 来源: [LangGraph ReAct Memory Agent](https://github.com/langchain-ai/memory-agent) (channel: web)
